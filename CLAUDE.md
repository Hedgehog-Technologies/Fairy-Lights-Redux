# Claude Code Guidelines

## Code Style

- When modifying existing code, match the patterns already in the file.
- If the file registers things one way (events, deferred registers, lambdas), don't switch to another.
- Match the existing style, even if you'd do it differently.

---

## Abstractions

- Do not create abstractions unless they reduce real, measurable complexity.
- No interfaces with a single implementation, except platform services in `common` (see Architecture), which have one implementation per loader.
- No factory methods that produce one type.
- No wrapper classes that just delegate to another class.
- Three similar lines of code is better than a premature abstraction.

---

## Comments

- Default to writing no comments.
- Only add a comment when the WHY is non-obvious.
- Never comment WHAT the code does.
- Never reference the current task, ticket, or fix in a comment.

---

## Scope

- Keep changes scoped to exactly what was requested.
- Don't "improve" adjacent code.
- Don't refactor things that aren't broken.
- Don't add features that weren't asked for.

---

## Error Handling

- Don't add error handling for scenarios that can't happen.
- Trust internal method contracts.
- Only validate at system boundaries: network packets, NBT/data components read from disk, resource and data pack loading, config files.

---

## Stack

- Language: Java 21
- Build: Gradle (use the wrapper, `./gradlew`)
- Minecraft 1.21.8, Parchment mappings (Mojang names)
- Loaders: Fabric (Loom, Fabric API), NeoForge, Forge
- Mixin for injecting into vanilla code
- Versions live in `gradle.properties`; only change them when asked.

---

## Project Structure

- `common/` - Loader-independent code, shared mixins, and shared assets/data
- `fabric/`, `neoforge/`, `forge/` - Loader entrypoints, platform implementations, loader mixins, and metadata (`fabric.mod.json`, `neoforge.mods.toml`, `mods.toml`)
- `buildSrc/` - Gradle convention plugins (`multiloader-common`, `multiloader-loader`)
- `old/` - The legacy 1.20.1 Forge mod (`me.paulf.fairylights`), kept as a porting reference. Read-only.
- `docs/` - `fairy-lights-redux/` holds the mod's docs (`interactions.md`, `recipes.md`, `notes.md`); `multiloader-template/` is the template documentation

Package: `org.hedgetech.fairylightsredux`. Mod id: `fairylightsredux`.

---

## Architecture

- Shared logic goes in `common`. It must not import loader APIs (`net.fabricmc`, `net.minecraftforge`, `net.neoforged`).
- Loader-specific behavior goes behind a service interface in `common` (see `IPlatformHelper`, loaded through `Services`).
- A new platform service needs the interface in `common`, an implementation in all three loaders, and a `META-INF/services` file in each loader.
- Mixins: shared ones go in `common`, loader-specific ones in that loader. Register each in the matching `*.mixins.json`.
- Keep mixins minimal. Prefer loader events or API hooks when one exists.

---

## Naming Conventions

- Classes: PascalCase
- Methods and fields: camelCase
- Constants: SCREAMING_SNAKE_CASE
- Packages: lowercase, under `org.hedgetech.fairylightsredux`
- Mixin classes: `Mixin<TargetClass>`
- Resource locations, asset and data file names: snake_case, namespace `fairylightsredux`

---

## Resources and Data

- Shared assets and data (models, blockstates, textures, lang, recipes, loot tables, tags) live in `common/src/main/resources`.
- Loader-specific metadata stays in that loader's resources.
- Keep lang keys, model paths, and registry ids consistent with each other.

---

## Porting from `old/`

- Port behavior, not code verbatim. Check for 1.21.8 API and mapping changes first.
- Don't modify anything under `old/`.
- Lights render through `UnsortedRenderType`, so models depend on emission order. Flat planes whose back face would sample an opaque texture emit only their front face, and glow shells must not land on another shell's plane.
- Special recipes are plain `CustomRecipe` classes in `server/item/crafting`, registered in `FLCraftingRecipes`, with JSON generated by `SpecialRecipeBuilder` in `FLRecipeProvider` (`./gradlew :neoforge:runData`). A colored item with a fixed shape uses `FLRecipeProvider.dyed()`. Don't port the old `GenericRecipe` engine.
- Update `docs/fairy-lights-redux/interactions.md` and `recipes.md` when an interaction or recipe is added or changed. Record porting decisions and caveats in `notes.md`.

---

## Build Configuration

- Every field added to `gradle.properties` must also be added to the `expandProps` map in `buildSrc/src/main/groovy/multiloader-common.gradle`.
- Don't hand-edit generated or cached output: `build/`, `.gradle/`, `run/`.

---

## Verification

- After making changes, run `./gradlew build` before reporting done. Fix any failure first.
- To check behavior in game, use `./gradlew :fabric:runClient`, `:neoforge:runClient` or `:forge:runClient` (`runServer` exists for each too).
- Say which loaders you did not build or launch.
- There are no automated tests yet. If you add some, run them with `./gradlew test`, and never modify existing tests unless the change intentionally updates the behavior they cover.

---

## Security

- Never commit tokens, credentials, or signing keys.
- Never log sensitive data.
- Never put secrets in comments or test fixtures.

---

## Git

- Use conventional commit format: type(scope): description
    - Types: feat, fix, refactor, test, docs, chore
- Keep commits focused on one change.
- Don't mention AI or "generated" in commit messages.
- Never commit `build/`, `.gradle/`, `run/`, or IDE files.
- Whenever you add a "Co-Authored-By" line, note what the co-author contributed in the commit message body.

---

## Dependencies

- Don't add new dependencies for something a few lines of code can handle.
- Don't add new dependencies when existing ones, including vanilla Minecraft and the loader APIs, cover the use case.

---

## Communication

- When done, explain what you changed and why in 2-3 sentences.
- If you found something unexpected, mention it.
- If you made a judgment call, explain your reasoning.

---

## Terms

- "Port" means to adapt code from the old mod to the new mod, not to copy it verbatim.
- "Loader" means Fabric, NeoForge, or Forge.
